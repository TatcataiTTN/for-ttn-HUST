Mediation Query bán cấu trúc & Big Data Integration Challenges

Khi dữ liệu là XML/semi-structured, không thể chỉ viết 1 câu GAV đơn giản — cần decompose schema thành sub-trees. Và khi số nguồn lên tới hàng triệu, cả GAV lẫn LAV truyền thống đều vỡ trận.

PHẦN 1/3
01

Sinh Mediation Query cho dữ liệu bán cấu trúc

  • Decompose mediation schema thành sub-trees
  • Partial Mapping — ánh xạ 1 sub-tree với 1 nguồn cụ thể
  • Join Graph & kết hợp các partial mapping thành mediation query hoàn chỉnh

Vì sao XML/semi-structured khó hơn quan hệ?

Với dữ liệu quan hệ, 1 câu GAV map thẳng 1 bảng mediated vào biểu thức trên bảng nguồn. Với cây XML lồng nhau nhiều cấp, không có "1 bảng" để map — phải decompose mediation schema thành các sub-tree (root là node đa trị hoặc gốc cây, lá phải có ít nhất 1 text node), rồi xử lý từng sub-tree riêng.

Partial Mapping → Join Graph → Mediation Query

Quy trình 3 bước: (1) Với mỗi sub-tree, tìm phần tương ứng ở từng nguồn (partial mapping). (2) Tìm các phép join khả dĩ giữa các nguồn dựa trên key/reference-key, tạo thành join graph (node = nguồn, cạnh = điều kiện join). (3) Kết hợp các partial mapping (mỗi sub-tree 1 cái) thành 1 mediation query hoàn chỉnh — hợp hai mediation query cũng tạo ra 1 mediation query mới.

Kết quả
Output cuối là 1 truy vấn XQuery thực thi được, sinh ra cây XML đúng cấu trúc mediation schema từ nhiều nguồn XML rời rạc.
PHẦN 2/3
02

Vì sao tích hợp truyền thống 'vỡ trận' ở quy mô Big Data

  • Deep Web at Scale, Schema Explosion, Keyword Queries không có schema cố định
  • GAV/LAV đòi hỏi mapping chính xác — không khả thi với hàng triệu nguồn
  • PAYGO: bắt đầu lỏng lẻo, cải thiện dần theo thời gian

4 lý do Data Integration truyền thống không đủ

  • Deep Web at Scalehàng chục triệu nguồn ẩn sau form web — không thể thiết kế mapping thủ công cho từng nguồn
  • Schema Explosionhàng trăm nghìn schema khác nhau cùng miền dữ liệu ("database design by the masses")
  • Modeling Everythingdữ liệu trải khắp mọi lĩnh vực tri thức loài người — 1 mediated schema duy nhất là bất khả thi
  • Keyword Queriesngười dùng web gõ từ khoá, không viết SQL theo đúng mediated schema nào cả

PAYGO — Pay-As-You-Go Integration

Thay vì thiết kế mediated schema + mapping hoàn chỉnh trước (như GAV/LAV truyền thống), PAYGO bắt đầu với rất ít ràng buộc ngữ nghĩa, trả lời truy vấn "tốt nhất có thể" với những gì đã biết, rồi cải thiện dần theo thời gian/phản hồi người dùng.

Traditional DIPAYGO
Single Mediated Schema (thiết kế thủ công)Schema Clusters (tự động theo chủ đề)

Deterministic AnswersHeterogeneous Ranking (best-effort)
PHẦN 3/3
03

Dataspace, Probabilistic Schema & WebTables

  • Dataspace/DSSP — mô hình thay thế khi không đủ thời gian thiết kế mediated schema
  • Probabilistic Mediated Schema — tạo tự động bằng clustering, kèm xác suất
  • WebTables — tích hợp không cần mediated schema tường minh, dùng keyword search + ranking

Probabilistic Mediated Schema & Mapping

Thay vì 1 mediated schema "đúng duy nhất", hệ thống tạo nhiều phiên bản khả dĩ bằng clustering thuộc tính các nguồn, mỗi phiên bản kèm 1 trọng số xác suất. Tương tự, mỗi mapping cũng có nhiều khả năng kèm xác suất tin cậy — mô hình hoá đúng sự không chắc chắn (uncertainty) ở cả 2 tầng.

WebTables — khai thác 154 triệu bảng chất lượng cao trên Web

Không xây mediated schema, WebTables trích xuất hàng tỷ bảng HTML, lọc ra các bảng quan hệ chất lượng cao bằng phân loại thống kê, rồi xếp hạng theo từ khoá người dùng gõ (FeatureRank dùng đặc trưng bảng; SchemaRank cộng thêm độ nhất quán schema qua Pointwise Mutual Information).

Ý nghĩa
Đây là minh chứng PAYGO hoạt động thực tế ở quy mô Web — "tích hợp" bằng tìm-kiếm-và-xếp-hạng thay vì mapping tường minh.

✍️ Bài tập làm giấy (có lời giải)

Bài 1. Mediation schema XML gốc: <Library><Book title author/><Reviews score/></Library>. Giả sử Reviews là node đa trị (1 Book có nhiều Review). Hãy decompose thành các sub-tree theo đúng quy tắc đã học, và mô tả 1 partial mapping khả dĩ nếu có 2 nguồn: S1 (bảng Book: title, author) và S2 (bảng Review: book_title, score). [Bổ sung (dựa theo ví dụ Films/Director trong 2_mediationquery.pdf)]
Lời giải: 2 sub-tree: t1 = root Library → Book(title, author) [root của mediation schema, chứa text node title/author]. t2 = root Reviews (node đa trị) → score [root là node đa trị, có text node score].
Partial mapping: t1 ↔ S1.Book(title,author) (ánh xạ trực tiếp cột-cột). t2 ↔ S2.Review(score) với điều kiện join S1.Book.title = S2.Review.book_title (dùng làm reference key nối 2 sub-tree lại thành 1 mediation query hoàn chỉnh qua Join Graph).
Bài 2. So sánh Probabilistic Mediated Schema (PAYGO) với mediated schema truyền thống (GAV/LAV cố định) theo 3 tiêu chí: cách tạo ra, số lượng phiên bản, cách xử lý khi sai. [Bổ sung]
Lời giải: Cách tạo: truyền thống = chuyên gia thiết kế thủ công; PAYGO = tự động bằng clustering thuộc tính nguồn. Số phiên bản: truyền thống = đúng 1 duy nhất; PAYGO = nhiều phiên bản khả dĩ đồng thời, mỗi phiên bản kèm xác suất. Xử lý khi sai: truyền thống = phải sửa thiết kế thủ công (tốn thời gian, dừng hệ thống); PAYGO = tự cải thiện dần qua phản hồi người dùng/dữ liệu mới, không cần dừng hệ thống hay sửa thủ công.

💬 Bài tập hỏi đáp nhanh

Bấm vào từng câu hỏi để lật xem đáp án — ôn tập nhanh thuật ngữ & khái niệm cốt lõi.

❓ Khi decompose mediation schema XML, root của 1 sub-tree phải thoả điều kiện gì?
💡 Là node đa trị (multi-value) hoặc là root của mediation schema, và sub-tree có ít nhất 1 text node.
❓ Join Graph dùng để làm gì trong sinh mediation query?
💡 Biểu diễn các phép join khả dĩ giữa các nguồn, dựa trên key/reference-key — node=nguồn, cạnh=điều kiện join.
❓ PAYGO khác Data Integration truyền thống ở nguyên lý cốt lõi nào?
💡 Bắt đầu với ít ràng buộc ngữ nghĩa, trả lời tốt nhất có thể ngay, cải thiện dần theo thời gian — không chờ thiết kế hoàn chỉnh.
❓ WebTables xếp hạng bảng kết quả bằng 2 phương pháp nào?
💡 FeatureRank (dùng đặc trưng bảng) và SchemaRank (cộng thêm độ nhất quán schema qua Pointwise Mutual Information).
