Data Integration — Tổng quan & Dị biệt dữ liệu

Data Integration là lớp trừu tượng bậc cao hơn DBMS: cho người dùng 1 giao diện truy vấn thống nhất tới nhiều nguồn dữ liệu độc lập, dù chúng khác nhau ở mọi tầng — từ hệ thống tới ngữ nghĩa.

PHẦN 1/3
01

Data Integration là gì

  • DBMS = trừu tượng hoá logic/vật lý; Data Integration = trừu tượng hoá bậc cao hơn
  • Mediated Schema — giao diện thống nhất duy nhất người dùng nhìn thấy
  • Wrapper — cầu nối giữa truy vấn và dữ liệu nguồn thật

Data Integration: một tầng trừu tượng mới

DBMS cho ta trừu tượng logical vs physical — người dùng viết SQL mà không cần biết dữ liệu lưu trên đĩa ra sao. Data Integration đi xa hơn: cho người dùng 1 giao diện truy vấn duy nhất (Mediated Schema) mà không cần biết dữ liệu thật nằm ở nguồn nào, mô hình gì, viết bằng ngôn ngữ gì.

3 thứ Mediated Schema giúp "độc lập"
Vị trí & nơi lưu trữ nguồn · Mô hình dữ liệu & cú pháp (SQL/XML/JSON...) · Biến thể ngữ nghĩa giữa các nguồn.

Wrapper — nơi 'dịch' truy vấn thành thao tác thật

Khi truy vấn trên Mediated Schema được viết lại (reformulate) thành truy vấn con cho từng nguồn, Wrapper là thành phần thực sự gửi thao tác đó tới nguồn (gọi API, chạy SQL cục bộ, parse HTML...), rồi chuyển kết quả trả về đúng mô hình dữ liệu nội bộ của hệ thống tích hợp.

Pipeline Query Processing
Query → Query Reformulation → Query Optimizer → Execution Engine → Wrapper(s) → Sources
PHẦN 2/3
02

7 mức độ Heterogeneity

  • System/Platform · Syntactic/Format · Structural/Schema
  • Semantic/Conceptual · Instance/Identity
  • Temporal/Process · Quality/Provenance/Governance

Dị biệt không chỉ là 'khác định dạng file'

Slide gốc chia dị biệt giữa các nguồn thành 7 tầng, từ thấp tới cao:

  • 1. System/Platformdữ liệu lưu ở đâu, truy cập bằng cách nào (SQL JDBC, Document API, Kafka topic...)
  • 2. Syntactic/Formatđịnh dạng file, encoding, cú pháp ngày/số (vd "2026-09-15" vs "15/09/26")
  • 3. Structural/Schemabảng, thuộc tính, khoá, độ chi tiết (granularity) khác nhau
  • 4. Semantic/Conceptualđồng nghĩa (synonym), đa nghĩa (homonym) — cần ontology để giải quyết

3 tầng còn lại — thường bị bỏ sót

  • 5. Instance/Identitycùng 1 thực thể thật xuất hiện khác nhau ở 2 nguồn — giải quyết bằng Entity Resolution/Record Linkage (buổi 4)
  • 6. Temporal/Processtần suất cập nhật khác nhau, dữ liệu "mới nhất" ở nguồn này có thể cũ hơn nguồn kia
  • 7. Quality/Provenance/Governanceđộ tin cậy, nguồn gốc, quyền truy cập dữ liệu khác nhau giữa các nguồn
Khung quan trọng nhất môn học
3 buổi tiếp theo lần lượt giải quyết đúng các tầng này: buổi 3 giải quyết tầng 3-4 (Schema Alignment), buổi 4 giải quyết tầng 5 (Record Linkage) — rồi tới Data Fusion xử lý xung đột giá trị khi đã gộp.
PHẦN 3/3
03

Kiến trúc: Virtual vs. Warehouse

  • Virtual Integration — truy vấn thời gian thực qua wrapper, dữ liệu ở nguyên nguồn
  • Data Warehousing — copy định kỳ (ETL) về kho tập trung
  • 5V của Big Data & pipeline 3 bước tổng thể

5V & pipeline tổng thể của môn học

Volume · Velocity · Variety · Veracity · Value — 5 tiêu chí định nghĩa Big Data. Toàn bộ nội dung môn học đi theo đúng 1 pipeline 3 bước xử lý Big Data Integration:

Pipeline tổng thể
Schema Alignment → Entity Resolution → Data Fusion
Đây chính là 3 buổi học tiếp theo
Buổi 3: Schema Alignment (GAV/LAV/GLAV). Buổi 4: Entity Resolution (Record Linkage). Data Fusion (Survivorship Rule) là bước ứng dụng cụ thể khi làm project.

✍️ Bài tập làm giấy (có lời giải)

Bài 1. Một mediated schema có quan hệ Flight(FlightNo, From, To, Date). Nguồn S1 là 1 API JSON trả {flight_id, origin, dest, date, status}, nguồn S2 là 1 bảng SQL FlightSchedule(fno, dep_airport, arr_airport, dep_date). Với mỗi nguồn, hãy chỉ ra: (a) mức độ Heterogeneity cụ thể nào xuất hiện so với mediated schema, (b) Wrapper cần làm gì để chuyển dữ liệu nguồn đó về đúng mô hình mediated schema. [Bổ sung (dựa theo ví dụ slide 'Movie' buổi 3, áp dụng ngược cho buổi 2)]
Lời giải: S1 (JSON API): (a) System/Platform Heterogeneity (API JSON ≠ mô hình quan hệ của mediated schema) + Syntactic/Format (field name flight_id/origin/dest khác tên cột FlightNo/From/To). (b) Wrapper gọi API, parse JSON, đổi tên field (flight_id→FlightNo, origin→From, dest→To), bỏ field 'status' không cần (hoặc giữ lại nếu mediated schema mở rộng).
S2 (SQL): (a) chỉ có Syntactic/Format Heterogeneity (khác tên cột: fno/dep_airport/arr_airport/dep_date), KHÔNG có System Heterogeneity vì cùng là quan hệ/SQL. (b) Wrapper chỉ cần viết 1 SQL SELECT với alias đổi tên cột, không cần parser phức tạp như S1.
Bài 2. Vì sao PAYGO coi 'Keyword Queries' là một thách thức riêng so với Data Integration truyền thống? Cho 1 ví dụ truy vấn từ khoá và giải thích vì sao GAV/LAV không áp dụng được trực tiếp cho nó. [Bổ sung]
Lời giải: GAV/LAV đòi hỏi truy vấn được viết dưới dạng hình thức (SQL/logic) trên MỘT mediated schema đã biết trước, để reformulate chính xác qua unfolding/views. Truy vấn từ khoá như 'chung cư quận 7 giá dưới 3 tỷ' không gắn với bất kỳ thuộc tính/quan hệ cụ thể nào của 1 schema — không có cách 'unfold' nó thành truy vấn logic rõ ràng trên nguồn, vì người dùng không biết (và không cần biết) mediated schema tồn tại hay có cấu trúc gì. PAYGO giải quyết bằng tìm-kiếm-và-xếp-hạng (như WebTables FeatureRank/SchemaRank) thay vì ánh xạ hình thức.

❓ Mediated Schema là gì?
💡 Giao diện truy vấn thống nhất duy nhất người dùng thấy, che giấu vị trí/mô hình dữ liệu/khác biệt ngữ nghĩa của các nguồn phía sau.
❓ Wrapper làm nhiệm vụ gì trong pipeline Query Processing?
💡 Nhận truy vấn đã reformulate, gửi thao tác thật tới nguồn dữ liệu, chuyển kết quả trả về đúng mô hình dữ liệu nội bộ.
❓ 7 mức độ Heterogeneity gồm những gì?
💡 System/Platform, Syntactic/Format, Structural/Schema, Semantic/Conceptual, Instance/Identity, Temporal/Process, Quality/Provenance/Governance.
❓ Instance/Identity Heterogeneity giải quyết bằng kỹ thuật nào, học ở buổi nào?
💡 Entity Resolution / Record Linkage — buổi 4 (Module 04 của site này).
❓ Ưu điểm chính của Data Warehousing so với Virtual Integration?
💡 Có thể chạy tính toán nặng (data mining/ML) trên bản copy mà không làm phiền nguồn gốc mỗi lần truy vấn.
❓ 3 bước pipeline tổng thể của Big Data Integration là gì?
💡 Schema Alignment → Entity Resolution → Data Fusion.
