Câu 1: Kiến trúc tổng thể của Hadoop

Trình bày kiến trúc tổng thể của Hadoop; vai trò của HDFS, MapReduce và YARN.

Thành phầnVai trò
HDFSLưu tệp lớn tin cậy trên cụm: chia block, nhân bản 3 lần
MapReduceMô hình lập trình xử lý batch song song, người dùng chỉ viết Map và Reduce
YARNQuản lý tài nguyên và lập lịch, cho nhiều ứng dụng chạy chung một cụm
Hadoop CommonThư viện và tiện ích dùng chung
Kiến trúc scale-out
Mở rộng bằng cách thêm máy phổ thông, coi hỏng hóc là bình thường: tự nhân bản dữ liệu, tự chuyển tác vụ sang node khác. Hadoop 1.x: MapReduce vừa xử lý vừa quản lý tài nguyên. Hadoop 2.x: YARN tách phần quản lý tài nguyên, MapReduce chỉ còn là một framework cạnh Spark, Flink, Tez.

Câu 3: Chia block và nhân bản trong HDFS

Quy trình
  1. Tệp được chia thành các block, mặc định 64 MB hoặc 128 MB.
  2. Mỗi block nhân bản mặc định 3 bản trên 3 DataNode khác nhau.
  3. Ví dụ tệp 1 GB, block 128 MB: 8 block, 24 bản sao, cần khoảng 3 GB dung lượng thật.
  4. Một DataNode hỏng: dữ liệu không mất vì còn bản ở node khác; NameNode tự điều phối sao chép lại cho đủ 3 bản.
Tính sẵn sàng và chịu lỗi
Chịu lỗi nằm ở tầng phần mềm (nhân bản), không cần phần cứng đắt tiền và không cần quản trị viên can thiệp.

Điểm lỗi duy nhất
NameNode giữ toàn bộ metadata. Secondary NameNode định kỳ sao lưu và hợp nhất edit log để phục hồi nhanh metadata; đây là điểm khôi phục, không phải bản sao chạy song song thay thế ngay.

Câu 5: Khi nào chọn Hive thay vì Pig

Chọn Hive khi
  1. Người dùng quen SQL và không muốn học lập trình.
  2. Dữ liệu dạng bảng, mục tiêu là báo cáo, tổng hợp, phân tích kinh doanh hoặc tích hợp công cụ BI.
  3. Chấp nhận độ trễ batch cỡ phút.
Chọn Pig khi
  1. Cần nhiều bước biến đổi hoặc join phức tạp, viết thành một script tuần tự dễ bảo trì.
  2. Cần chèn logic riêng bằng UDF (Java, Python).
Điểm chung
Cả hai đều nhằm đơn giản hoá việc dùng Hadoop và cuối cùng quy về job MapReduce chạy trên cụm.

Câu 6: Các bước thực thi một chương trình MapReduce

BướcViệc xảy ra
1. Input splitDữ liệu trên HDFS chia thành split, mỗi split giao một map task, ưu tiên chạy ở node giữ block
2. MapĐọc từng bản ghi, sinh cặp (key, value) trung gian, ghi ra đĩa cục bộ; Combiner có thể gộp cục bộ trước
3. ShuffleChia cặp trung gian theo key cho các reducer (hash(key) mod R), reducer kéo phần của mình qua mạng; bước tốn kém nhất
4. SortMỗi reducer sắp theo key, gom thành (key, [value, ...])
5. ReduceGọi hàm reduce cho từng key, ghi output lên HDFS, mỗi reducer một file
Chịu lỗi
Tác vụ lỗi hoặc node hỏng được framework tự chạy lại.

Câu 6: Ví dụ đếm từ (WordCount) với 2 split

Giai đoạnNội dung
Split 1hadoop hdfs hadoop
Split 2hdfs yarn hadoop
MapMap 1: (hadoop,1) (hdfs,1) (hadoop,1)  |  Map 2: (hdfs,1) (yarn,1) (hadoop,1)
Shuffle và Sort (2 reducer)R1: hadoop → [1,1,1]  |  R2: hdfs → [1,1], yarn → [1]
Reduce(hadoop,3) (hdfs,2) (yarn,1)
Với Combiner
Dùng chính hàm cộng làm Combiner: Map 1 gửi (hadoop,2) (hdfs,1) thay vì 3 cặp, giảm lưu lượng shuffle.

Câu 7: Mã Python (Hadoop Streaming) và kết quả

sales_mapper.py
#!/usr/bin/env python3
import sys
for line in sys.stdin:
    f = line.strip().split(",")
    if len(f) != 5 or f[0] == "order_id":
        continue
    print(f"{f[1]}\t{float(f[4])}")
sum_reducer.py
#!/usr/bin/env python3
import sys
cur, total = None, 0.0
for line in sys.stdin:
    k, v = line.rstrip("\n").split("\t")
    if k != cur:
        if cur is not None:
            print(f"{cur}\t{total}")
        cur, total = k, 0.0
    total += float(v)
if cur is not None:
    print(f"{cur}\t{total}")
python3 sales_mapper.py < sales.csv | sort | python3 sum_reducer.py
C001    40.0
C002    10.5

Chạy thử cục bộ, sort mô phỏng shuffle. Trên cụm: hadoop jar hadoop-streaming.jar -mapper sales_mapper.py -combiner sum_reducer.py -reducer sum_reducer.py

Câu 8: Nguyên nhân MapReduce kém hiệu quả khi dữ liệu lệch

Cơ chế gây lệch
  1. Reducer được chọn theo hash(key) mod R: mọi bản ghi của một khoá đi về cùng một reducer.
  2. Một khoá chiếm phần lớn bản ghi (khách VIP, giá trị null, ngày khuyến mãi) làm reducer đó quá tải.
  3. Reducer này chạy lâu hơn nhiều (straggler), cả job phải chờ; các reducer khác ngồi không nên thêm máy cũng không nhanh hơn.
  4. Reducer quá tải có thể tràn bộ nhớ hoặc đĩa; join có khoá nóng gặp lỗi tương tự.

Câu 8: Kỹ thuật cải thiện hiệu suất

Kỹ thuậtCách làmĐiều kiện

SaltingGiai đoạn 1: khoá thành key#k (k ngẫu nhiên trong K) để chia khoá nóng cho K reducer. Giai đoạn 2: bỏ hậu tố, gộp tiếpTính từng phần rồi gộp được

Skew joinXử lý riêng khoá nóng; bảng nhỏ đưa vào bộ nhớ mọi mapper (map-side join); Pig skewed join, Hive skew joinMột bảng đủ nhỏ, hoặc biết khoá nóng
Tách khoá đặc biệtXử lý riêng null, giá trị mặc địnhBiết khoá gây lệch

Câu 9: Kiến trúc pipeline phân tích log truy cập

Website thương mại điện tử lưu lượng lớn: thu thập log real-time, lưu lâu dài, phân tích hành vi người dùng.

YARN chạy Spark, Flink, Hive. ZooKeeper phục vụ điều phối (HBase, HDFS HA, Kafka bản cũ).

Câu 9: Đáp ứng ba yêu cầu của đề

Yêu cầuThành phầnCách làm
Thu thập log real-time KafkaWeb server là producer, gửi vào topic access_logs; nhiều partition (khoá theo user_id hoặc session_id), nhân bản 3, giữ cấu hình được (ví dụ 7 ngày) để đọc lại
Lưu trữ log lâu dài HDFSSpark, Flink hoặc Kafka Connect ghi Parquet hoặc ORC, phân vùng dt/hour, nhân bản 3
Phân tích hành vi người dùng Hive, Spark, FlinkHive batch trên bảng external theo phân vùng; Flink hoặc Spark Streaming tính chỉ số theo cửa sổ thời gian
Điều phối định kỳ OozieCoordinator mỗi giờ hoặc ngày: gộp file nhỏ, thêm partition, chạy HiveQL, Sqoop xuất kết quả, gửi thông báo
Lưu ý thiết kế
Gom log thành tệp lớn (vài trăm MB) vì HDFS kém với tệp nhỏ; dùng định dạng cột để Hive đọc ít dữ liệu; Kafka là bộ đệm nên consumer chậm hoặc gián đoạn không làm mất log; cần tra theo userID độ trễ thấp thì ghi thêm vào HBase.

Câu 9: Ví dụ HiveQL cho phân tích hành vi

CREATE EXTERNAL TABLE access_logs (
  user_id STRING, session_id STRING, url STRING,
  action STRING, ts TIMESTAMP)
PARTITIONED BY (dt STRING, hour STRING)
STORED AS PARQUET LOCATION '/data/access_logs';

-- Top 10 sản phẩm được xem nhiều nhất trong ngày
SELECT url, COUNT(*) AS views
FROM access_logs WHERE dt = '2023-01-01' AND action = 'view'
GROUP BY url ORDER BY views DESC LIMIT 10;
-- Tỉ lệ chuyển đổi theo ngày
SELECT dt,
  COUNT(DISTINCT CASE WHEN action='purchase'
        THEN session_id END) /
  COUNT(DISTINCT CASE WHEN action='view'
        THEN session_id END) AS conversion
FROM access_logs GROUP BY dt;

Bảng external trỏ vào thư mục log, truy vấn chỉ đọc phân vùng cần dùng.

Câu 10: Số dư cuối của mỗi account_id, ý tưởng

map(dòng):
    bỏ qua header
    nếu type == "deposit":     emit(account_id, +amount)
    nếu type == "withdrawal":  emit(account_id, -amount)

reduce(account_id, danh_sách_giá_trị):
    emit(account_id, sum(danh_sách_giá_trị))
Thứ tự không quan trọng
Phép cộng giao hoán và kết hợp nên số dư cuối không phụ thuộc thứ tự giao dịch: không cần cột timestamp, và có thể dùng reducer làm Combiner.

Câu 10: Mã Python và kết quả

bal_mapper.py
#!/usr/bin/env python3
import sys
for line in sys.stdin:
    f = line.strip().split(",")
    if len(f) != 5 or f[0] == "transaction_id":
        continue
    amount = float(f[3])
    if f[2] == "deposit":
        print(f"{f[1]}\t{amount}")
    elif f[2] == "withdrawal":
        print(f"{f[1]}\t{-amount}")

python3 bal_mapper.py < transactions.csv \

A102    1000.0
